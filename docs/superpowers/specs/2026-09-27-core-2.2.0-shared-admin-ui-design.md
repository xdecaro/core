# Core 2.2.0 Shared Admin UI

**Date:** 2026-09-27  
**Status:** Proposed design for review  
**Owner:** xdecaro Joomla ecosystem  
**Target:** Joomla 6.1.3 only, PHP 8.3+

## Goal

Promote the mature, reusable administrator UI patterns already present in Core 2.1.0 into a supported public UI contract for the whole xdecaro ecosystem.

Core 2.2.0 must provide one shared visual and responsive foundation that can be consumed by People, Courses, Organizations, Membership, Competitions, Photos and later xdecaro products without copying Core component CSS or creating incompatible per-product mobile fixes.

The shared UI must preserve product independence: Core owns presentation primitives and responsive behavior, while each consuming component continues to own its domain model, controllers, forms, permissions, data and business logic.

## Why this change belongs in Core

Core 2.1.0 already separates three useful layers:

1. foundation styles in the system plugin (`core.css`);
2. reusable UI components in the system plugin (`components.css`);
3. a richer administrator suite currently implemented mainly inside `com_xdecarocore` (`admin.css` and `responsive.css`).

The third layer contains generic patterns such as page headers, hero blocks, KPI metrics, information cards, diagnostics, notices and responsive tables, but because it is packaged as private component styling it is not a clean dependency for other xdecaro products.

As a result, products such as People have accumulated their own administrator CSS for dashboard, information, duplicate review and person editing. This creates duplicated responsive rules and inconsistent mobile behavior.

Core 2.2.0 formalizes the generic administrator layer as a public opt-in asset instead of duplicating or globally injecting styles.

## Design principles

### 1. Opt-in, never global

Shared administrator UI must be loaded explicitly by a consumer through Core's public asset service. Core must not inject the UI globally into Joomla administrator pages.

### 2. Scoped styles

All shared administrator rules must be scoped under an xdecaro wrapper so they cannot unexpectedly restyle Atum or unrelated extensions.

Canonical page structure:

```html
<div class="xdecaro-scope xdecaro-suite">
    ...
</div>
```

A consumer may add product-specific classes to the same wrapper, but the Core contract is based on `xdecaro-scope` and `xdecaro-suite`.

### 3. Core owns UI behavior, not product behavior

Core may define responsive layout, visual state, spacing, tables, forms and common interaction presentation. It must not know about People records, Courses editions, Membership rules, Competition rosters, Organizations governance or any other product domain.

### 4. Mobile is part of the contract

A shared component is not considered complete if it only renders correctly on desktop. Mobile behavior is part of the public Core UI API and must be tested as such.

### 5. Do not hide overflow defects

The shared layer must fix layout causes rather than applying page-wide `overflow-x: hidden`. A large table may scroll inside its dedicated wrapper; the entire administrator page must not become wider than the available content area.

### 6. Keep the existing visual language

Core 2.2.0 should promote and consolidate the existing `xdecaro-suite` language rather than rename every mature class. Compatibility and incremental migration are preferred over aesthetic renaming.

## Public asset architecture

Core 2.2.0 exposes three ordered style layers.

```text
xdecaro.core
    ↓
xdecaro.components
    ↓
xdecaro.admin
```

### `xdecaro.core`

Foundation only:

- design tokens;
- colors;
- spacing;
- radius;
- shadows;
- typography foundations;
- theme/dark-mode variables.

### `xdecaro.components`

Small reusable controls:

- card;
- toolbar;
- button;
- badge;
- field;
- input/select/textarea;
- basic table;
- empty state;
- loader;
- modal;
- focus-visible behavior.

### `xdecaro.admin`

New public administrator layout layer. It depends on `xdecaro.components`, which depends on `xdecaro.core`.

Physical plugin layout:

```text
plg_system_xdecarocore/
└── media/
    └── css/
        ├── core.css
        ├── components.css
        └── admin.css
```

The shared administrator asset is owned by the system plugin/public Core runtime, not by `com_xdecarocore`.

## AssetService public API

Core's `AssetService` remains the supported loading boundary.

Existing public methods remain valid. Core 2.2.0 adds an administrator method and public asset identifier equivalent to:

```php
public const STYLE_ADMIN = 'xdecaro.admin';

public function useAdminUi(WebAssetManager $assets): void;
```

`useAdminUi()` must activate the full dependency chain through Joomla Web Asset Manager dependency metadata rather than manually loading duplicate files.

Consumer example:

```php
$assetService->useAdminUi($this->document->getWebAssetManager());
```

Consumers must not load files from `com_xdecarocore` directly.

## Public `xdecaro-suite` contract

The following existing generic Core patterns become supported public administrator primitives.

### Page structure

- `.xdecaro-suite`
- `.xdecaro-suite__hero`
- `.xdecaro-suite__page-header`
- `.xdecaro-suite__eyebrow`
- `.xdecaro-suite__section`
- `.xdecaro-suite__actions`
- `.xdecaro-suite__count-badge`

A product should be able to produce the same visual hierarchy as the current Courses direction: eyebrow/context, strong page title, concise description, KPI block and clearly separated content sections.

### Metrics / KPI

- `.xdecaro-suite__metrics`
- `.xdecaro-suite__metric`

The public metric grid must be generic. It must not assume a five-item Core dashboard.

Default responsive behavior:

- wide desktop: auto-fit based on available width;
- tablet/intermediate containers: two or three columns as space allows;
- normal phone width: two columns when practical;
- narrow phone/container: one column.

The old "last metric spans the full row" behavior is not a default public rule. If Core's own dashboard still needs it, it must use an explicit Core-only or public modifier such as:

```text
.xdecaro-suite__metrics--fill-last
```

### Information and diagnostics

- `.xdecaro-suite__info-grid`
- `.xdecaro-suite__info-card`
- `.xdecaro-suite__info-card--full`
- `.xdecaro-suite__card-heading`
- `.xdecaro-suite__definition-list`
- `.xdecaro-suite__diagnostic-list`
- `.xdecaro-suite__diagnostic-row`
- `.xdecaro-suite__summary-bar`

These primitives must remain domain-neutral. Labels and values come from the consumer.

### Notices

- `.xdecaro-suite__notice`
- `.xdecaro-suite__notice-icon`
- `.xdecaro-suite__notice-content`

Notice styles may expose state modifiers (information, success, warning, danger) using Core tokens and Bootstrap/Joomla-compatible semantics.

### Responsive table

- `.xdecaro-suite__responsive-wrap`
- `.xdecaro-suite__responsive-table`
- `.xdecaro-suite__action-heading`
- `.xdecaro-suite__action-cell`

Generic responsive-table behavior is public. Core-specific extensions/update-table selectors remain private to `com_xdecarocore`.

## Patterns that remain private to `com_xdecarocore`

Core's own administrator component may keep selectors and behavior that model its product-specific dashboard, including patterns equivalent to:

- `.xdecaro-suite__products-table`;
- `.xdecaro-suite__product-row`;
- `.xdecaro-suite__extensions-table`;
- `.xdecaro-suite__extension-primary`;
- `.xdecaro-suite__extension-element-mobile`;
- `.xdecaro-suite__extension-element-cell`;
- `.xdecaro-suite__updates-table`;
- `.xdecaro-suite__update-status-cell`;
- `.xdecaro-suite__dashboard-products-table`;
- product-specific JavaScript such as package/extension row toggles.

A class is promoted only when it can be explained without referring to a Core-specific business entity.

## New public administrator primitives

Core 2.1.0 does not yet contain every pattern needed by current consumers. Core 2.2.0 adds the following generic primitives.

## Form layout

Public classes:

- `.xdecaro-form`;
- `.xdecaro-form-grid`;
- `.xdecaro-form-grid--2`;
- `.xdecaro-form-section`;
- `.xdecaro-form-help`;
- `.xdecaro-form-actions`.

Desktop form grids may use two columns when the fields are naturally paired. Mobile always prioritizes readable vertical flow.

### Joomla form bridge

Inside `.xdecaro-form`, standard Joomla administrator form markup becomes responsive without consumers rewriting every XML field:

- `.control-group`;
- `.control-label`;
- `.controls`.

At mobile widths/containers:

```text
Label
[ full-width control ]
```

Core must ensure common controls respect the available width:

```css
width: 100%;
min-width: 0;
max-width: 100%;
```

where appropriate for:

- text inputs;
- select elements;
- textarea;
- Choices wrappers;
- Joomla calendar/date controls;
- field groups;
- buttons inside form rows.

This rule is scoped to xdecaro form containers and must not globally rewrite Joomla administrator forms.

## Filter bar

Public classes:

- `.xdecaro-filterbar`;
- `.xdecaro-filterbar__search`;
- `.xdecaro-filterbar__filter`;
- `.xdecaro-filterbar__actions`.

Wide layout may render search, filters and actions in one row. On mobile they must wrap/stack to available width without forcing horizontal page overflow.

## Accordion

Public classes:

- `.xdecaro-accordion`;
- `.xdecaro-accordion__item`;
- `.xdecaro-accordion__button`;
- `.xdecaro-accordion__body`.

Core provides presentation only. Collapse behavior should continue to use Joomla/Bootstrap behavior rather than a second proprietary accordion runtime.

People's person editor is the first intended consumer after Core 2.2.0.

## Responsive contract

Responsive behavior must react to the real content width available inside Joomla administrator, not only to the browser viewport. Joomla's sidebar and administrator chrome may leave a narrow content column while the browser viewport is still comparatively wide.

Therefore Core 2.2.0 should prefer container-aware behavior for reusable complex patterns where supported and retain safe media-query fallbacks where required.

### Required target widths

The UI contract must be verified at least at effective content widths representative of:

- 320 px;
- 393 px;
- 430 px;
- 768 px;
- 1024 px;
- wide desktop.

The 393 px case is a mandatory regression target because it represents the mobile failure observed in current People administrator views.

### Universal sizing rules

Within the shared suite, important flex/grid children must be shrinkable:

```css
min-width: 0;
max-width: 100%;
```

as appropriate.

Cards, panels, sections and form wrappers must not establish accidental fixed minimum widths.

Long technical values such as UUIDs, hashes and filenames must wrap safely (`overflow-wrap`/equivalent) instead of widening the page.

### Tables

There are two supported responsive strategies:

1. a table remains a table but scrolls horizontally inside `.xdecaro-suite__responsive-wrap`;
2. a table with the documented `data-label` contract becomes a card/stacked row presentation below the defined container threshold.

Which strategy a consumer uses depends on the table's semantics. In both cases, only the table wrapper may scroll; the whole page must remain within the administrator content width.

### Safe area

Bottom spacing for mobile layouts may include `env(safe-area-inset-bottom)` within the xdecaro suite when required. Shared Core UI must not reposition or restyle Joomla's global header/sidebar solely to work around product content.

## Toolbar and actions

Shared product-level action groups must:

- wrap when space is constrained;
- retain touch-friendly hit areas;
- avoid fixed widths that force page overflow;
- preserve Joomla's standard action semantics and ACL checks.

Core 2.2.0 does not replace Joomla's administrator toolbar service. It provides layout primitives for product-owned action bars and section actions.

## Accessibility

The shared UI contract must preserve or improve administrator accessibility:

- visible `:focus-visible` state;
- semantic heading hierarchy owned by the consumer markup;
- adequate target size for mobile actions;
- no status encoded by color alone where a text/badge label is available;
- responsive transformations must preserve reading order;
- table-to-card transformations must retain header context through `data-label` or equivalent accessible text;
- accordion markup must preserve `aria-expanded`, `aria-controls` and focus behavior through Joomla/Bootstrap;
- reduced-motion preferences must not be defeated by new shared animations.

## Theme and dark mode

The administrator UI must continue to rely on Core/Joomla CSS variables rather than hardcoded light-theme colors wherever practical.

New primitives must be validated in the same theme modes supported by Core's existing foundation. Consumer products must not fork the shared asset just to obtain dark-mode compatibility.

## Version and platform policy

This is a public API expansion and therefore releases as **Core 2.2.0**, not 2.1.1.

Core 2.2.0 metadata must consistently declare the ecosystem platform policy:

- Joomla: **6.1.3 only**;
- PHP: **8.3 or newer**.

Existing stale CSS/version comments from older Core releases must be cleaned while moving rules, so source comments do not incorrectly describe the current asset contract.

## Core component migration

`com_xdecarocore` becomes a consumer of the same public UI it publishes.

Before:

```text
useComponents()
+ com_xdecarocore.admin
+ com_xdecarocore.responsive
```

Target:

```text
useAdminUi()
+ com_xdecarocore.admin   (Core-specific remainder only)
```

Generic administrator styles move to the plugin's public `admin.css`. The component's CSS keeps only Core-dashboard-specific selectors.

A separate component `responsive.css` should be removed or reduced only after every rule is classified as either public generic behavior or genuinely Core-specific behavior.

No rule is deleted merely because a new shared file exists; migration requires equivalence/regression verification.

## Consumer migration strategy

Migration is incremental. Core 2.2.0 must ship a complete public UI contract before product CSS is removed.

Recommended order:

1. **Core itself** — validate the public contract without changing domain behavior.
2. **People** — first external consumer because current person/information mobile defects exercise forms, accordion, cards, diagnostics, backup tables and long technical values.
3. **Courses** — align its current visual direction with the shared contract and remove any equivalent local primitives.
4. **Organizations**.
5. **Membership**.
6. **Competitions**.
7. **Photos**.
8. Remaining xdecaro products as they are reviewed.

A consumer migration must keep product-specific CSS for domain-specific layouts. The goal is not "no local CSS"; the goal is "no duplicated shared UI foundation".

## Compatibility policy

Core 2.2.0 must not break existing consumers of `xdecaro.core` or `xdecaro.components`.

The new `xdecaro.admin` layer is additive and opt-in.

Existing `xdecaro-suite` markup inside Core should remain visually compatible after its generic rules move to the public asset.

No consumer is required to migrate in the same release as Core 2.2.0.

## Testing and release gates

Core 2.2.0 is not complete until automated and runtime validation covers the shared contract.

### Static/contract tests

Tests must verify:

- the public `xdecaro.admin` Web Asset exists;
- dependency order is `xdecaro.admin` → `xdecaro.components` → `xdecaro.core`;
- `AssetService::useAdminUi()` exists and loads the public asset;
- public CSS lives in the Core plugin/public runtime rather than `com_xdecarocore`;
- generic suite selectors are present in the public asset;
- Core-product-only selectors remain outside the public contract;
- Joomla form bridge selectors are scoped under xdecaro form/suite classes;
- responsive table/card contract is present;
- no global `body`, `#header`, sidebar or generic Joomla selector is introduced without xdecaro scope;
- manifest/platform metadata is Core 2.2.0, Joomla 6.1.3 and PHP 8.3+.

### Build tests

Validate:

- deterministic package build;
- expected package members;
- Web Asset registry integrity;
- syntax/lint checks;
- SHA-256 generation;
- Joomla updater metadata.

### Runtime tests

At minimum:

- clean install on Joomla 6.1.3;
- upgrade from Core 2.1.0 to 2.2.0;
- existing Core dashboard remains functional;
- existing `useFoundation()` and `useComponents()` consumers remain functional;
- `useAdminUi()` loads its dependency chain exactly once;
- no styling leaks into an administrator page that does not opt in.

### Responsive regression tests

The project must add a practical responsive contract. It may combine source assertions and browser/runtime probes, but it must explicitly verify the failure classes observed in current consumers:

- xdecaro page width does not exceed available container width;
- Joomla form label/control stacks on narrow containers;
- selects/Choices/date controls remain inside the form section;
- KPI grids do not use a five-item-specific rule by default;
- long hashes/UUIDs/filenames wrap;
- filters/actions wrap or stack;
- responsive table wrapper contains horizontal overflow;
- card conversion preserves labels;
- accordion width remains within the container.

## Acceptance criteria for the first People migration

Although People changes are a separate release, Core 2.2.0 is designed to support these acceptance criteria without adding another shared foundation inside People:

- People Information renders correctly at 393 px without clipped left content or page-level horizontal overflow;
- Person edit accordion remains full-width and readable;
- standard Joomla form rows stack vertically on mobile, including country/select fields;
- Choices and date controls do not overflow their accordion body;
- dashboard and information grids collapse consistently;
- backup tables and hashes are contained;
- existing People business logic and permissions remain unchanged.

If People requires a generally useful primitive to satisfy these criteria, that primitive should be considered for Core before adding another one-off People foundation.

## Documentation

Core 2.2.0 documentation must update `docs/asset-service.md` with:

- the three-layer asset model;
- `useAdminUi()` usage;
- required wrapper markup;
- public primitive catalogue;
- responsive table `data-label` contract;
- Joomla form bridge scope;
- guidance on what belongs in Core versus consumer CSS.

A short migration example should show one product page using the shared page header, KPI metrics, section, form/filter or table primitives without referencing Core component assets.

## Non-goals

Core 2.2.0 does **not**:

- redesign Joomla Atum globally;
- inject xdecaro UI into every administrator page;
- replace Joomla's toolbar, form XML system, ACL or Bootstrap runtime;
- move product business logic into Core;
- require all ecosystem products to migrate simultaneously;
- remove every product-local stylesheet;
- rename existing public suite classes solely for style consistency;
- create a JavaScript framework for layout behavior that CSS/Joomla/Bootstrap already handles;
- change database schemas or business APIs as part of the UI consolidation.

## Definition of done

Core 2.2.0 Shared Admin UI is done when:

1. `xdecaro.admin` is a documented public, opt-in Web Asset with the correct dependency chain;
2. `AssetService::useAdminUi()` is the supported loading API;
3. generic existing `xdecaro-suite` rules are promoted from the Core component to the public asset without visual regression;
4. forms, filters and accordion primitives are available for consumers;
5. shared responsive behavior covers narrow Joomla administrator containers and prevents page-level overflow;
6. Core's own component uses the public admin asset and keeps only domain-specific styling locally;
7. Joomla 6.1.3 / PHP 8.3+ metadata is consistent;
8. clean install, 2.1.0 upgrade, deterministic build and UI contract tests are green;
9. documentation defines the public class/API boundary clearly;
10. no consumer private table/API or business logic changes are required by this release.
